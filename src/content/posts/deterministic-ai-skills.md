做工具类 AI Skill 时，有一个反直觉的陷阱：**大多数人都在优化提示词怎么写得更聪明，却很少去测“当模型拿不到工具时它会干什么”。**

最近整理几个贴近日常决策的确定性计算 Skill——覆盖离职赔偿（`severance-calculator`，12 条单测）、年终奖与全年并税最优分配（`annual-bonus-optimizer`，17 条单测）、房贷提前还款方案对比（`mortgage-prepay-calculator`，19 条单测），一共 48 条全由标准库 Python 驱动、零外部依赖的确定性测试——本以为把数学公式和分档临界点写死在脚本里就万事大吉了。

结果一次非交互命令行模式的回归测试，直接敲响了警钟。

## 一、那次让人后背发凉的“心算幻觉”

测的还是同一个城市、同一年份、同一套提示词输入。

唯一的不同，是在非交互（non-interactive）CLI 模式下，`Bash` 工具权限被默认拒绝了——模型执行不了本地的 Python 计算脚本。

按理想中的对齐逻辑，模型找不到计算器，应该直接停下来告诉用户：“当前权限无法执行脚本，请开启权限或由脚本运行。”

但它没有这么做。它**静默降级**了——在没人要求的情况下自己接管了所有数学运算，开始用“心算”一步步往外推税率和社平工资三倍封顶线。更荒唐的是，面对完全相同的上下文和年份，前后两次运行，模型自己“回忆”出了两个截然不同的本地社平工资上限数字：一次算成 **37,302**，另一次算成 **36,921**。

> 最可怕的不是大模型算错数，而是它会用**完全笃定的口吻、严丝合缝的 Markdown 表格格式**，把现编出来的假数字当成“依据官方脚本计算的结果”交给你。

一旦用户涉及的是“N+1 赔偿封顶线怎么算”、“多发 1 块钱年终奖是不是直接掉进税率跳档陷阱”，或者“还一笔本金到底选缩期还是减月供”，哪怕错一位小数点，决策方向都可能是反的。

## 二、用三层结构性护栏，把“估算”堵死

发现这个问题之后，单纯在 Prompt 里写一句“请务必调用脚本，不要瞎编”是不够的——在模型觉得“用户急着要答案，而工具不可用”的权衡下，软约束往往最先被牺牲。

最终落地的做法，是把每个确定性计算 Skill 改造成**三层结构化护栏**：

1. **工具声明前置（`allowed-tools: Bash,Read`）**：明确向执行环境声明所需最小权限集合，避免运行时临时因为权限策略模糊被悄无声息拦截。
2. **硬性数值契约（All numbers must come from script）**：在 Skill 指令里写死不可逾越的红线——正文里的每一个中间金额、封顶上限、临界点与总计数字，都必须来自刚执行过的脚本标准输出；只要没有看到真实的执行返回，**严禁输出具体算出的金额**。
3. **显式退化清单（Fallback without guessing）**：一旦真的拿不到执行权限或工具报错，立刻中断计算链路，改用预先写好的**纯公式 + 核对清单（Checklist）**模板向用户说明“怎么自己带入算”，宁可交一份空白框架，也绝不往空格里填 AI 自己猜出来的数字。

把“如果不给工具怎么办”写成显式分支之后，模型就不再需要“为了帮用户答出来而硬着头皮脑补数据”。

## 三、写工具类 Skill 时留下的四条硬原则

把这组小工具全部跑通、零外部依赖收口到 48 条测试全绿之后，我给自己记下了四条极简规则，之后写任何工具型 Skill 都照着这个尺子量：

| 原则 | 具体标准 | 为什么这样定 |
| :--- | :--- | :--- |
| **1. 名字即搜索词** | 用直白的场景关键词命名，不造玄乎黑话 | Skill 首先得被 Agent 或检索路由精准命中，起花名反而降召回 |
| **2. 输出即结果与表格** | 直接给出精确数字、临界差值和对比方案表 | 用户来问计算题是为了做决定，不是为了再读一遍八百字教科书 |
| **3. 极简输入** | 只收计算必需的 2–4 个核心变量，缺一补一 | 字段太多不仅烦人，还会让模型在缺参时自作主张乱填默认值 |
| **4. 零外部 API 依赖** | 全部用语言标准库计算，本地离线秒级返回 | 不受网络抖动、第三方接口挂掉或密钥过期影响，永远可复现 |

说到底，大语言模型是极好的交互界面与边界解释器，但只要场景里出现**税率跳档、月供折现、三倍封顶、日期差天数**这类确定性规则，算账这件事就应该 100% 交给冷冰冰的代码去跑。

让语言模型负责听懂人话，让确定性脚本负责守住数字——这两半各自站对位置，才算一个靠谱的工具。
