做多 Agent 系统，大多数 Demo 演示的是“怎么把一个复杂任务拆开、交给几个角色协作完成”。但真正放到工程里跑，happy path 往往只占两成工作量；决定系统能不能用的，是**剩下八成的失败路径**：

- 两个 Worker 同时去领同一个 `ready` 任务怎么办？
- 执行到一半进程被 `SIGKILL` 杀掉，恢复之后任务卡死在半空中怎么办？
- 上游预算明明超了，重试和失败的调用算不算钱？
- 写文件的时候，路径里藏了一个大小写折叠或者硬链接怎么办？

在搭建一个多 Agent 递归交付编排器（AgentCorp）和它独立的对抗性测试集（AgentCorpGauntlet）时，我决定把设计的中心倒过来：**先假设每一步都会出事，再反推正常的调度应该长什么样。**

## 一、把状态、事件与预算关进确定性护栏

Agent 可以有随机性，但**调度器与账本绝对不能有歧义**。整个系统在离线测试环境下跑了 310 条单元测试，开启严格静态类型检查（`mypy` strict）与代码规范检查（`ruff`），按职责拆成几层清晰的边界：

- **数据与事件层（`models` / `events` / `store`）**：所有状态变化优先追加写入只读事件流（append-only event log），每个 run 维护严格连续递增的 `run_seq`，确保回放和审计能对得上每一帧历史。
- **有向图与分解层（`graph` / `planner` / `decomposer`）**：显式校验任务依赖关系与状态转移矩阵（`ALLOWED_TRANSITIONS`），任何跨状态跳跃在落盘前就会被拒绝。
- **调度、执行与独立审查（`scheduler` / `worker` / `reviewer`）**：严格隔离执行者与审查者角色（`enforce_independence`），禁止任何任务“自己审自己”。
- **可靠性与预算熔断（`reliability` / `budget` / `chaos` / `supervisor`）**：把令牌上限、美元成本上限、最大派发次数和挂钟超时（wall clock）设为四道硬顶；同时内置混沌注入模块，专门模拟超时、中断与异常返回。

状态转移的双重校验不是为了写起来好看，而是为了堵住并发和恢复时最容易出现的“状态漂移”。

## 二、高并发抢占：一条 SQL 比十句锁更老实

当多个 Worker 进程或线程同时轮询任务池时，常见的写法是“先查出 `status == 'ready'` 的任务，再更新成 `running'`”。在单线程 Demo 里这毫无问题，一旦并发上来，就会变成典型的 Check-Then-Act 竞态——两个 Worker 拿到同一份任务，干两份重复的活，烧两份 Token。

这里没有依赖脆弱的内存锁，而是把竞争收口到 SQLite 的单条原子条件更新 `Store.claim_task` 上：

```sql
UPDATE tasks
SET status = 'running',
    worker_id = ?,
    claimed_at = ?
WHERE id = ? AND status = 'ready';
```

配合 `busy_timeout = 5000` 与影响行数校验，只有真正抢到行锁、将 `status` 从 `ready` 改写为 `running` 的那一方才算认领成功；后来者受影响行数为 `0`，直接退避去领下一个任务。在测试中，我们用 **64 线程 + 64 进程** 并发压测抢占逻辑，没有任何任务被重复认领。

## 三、独立红队测试：“拒绝优先”才测得出真问题

写完主系统之后，自己给自己写单测很容易陷入确认偏误——写代码的人太清楚“应该怎么传参”，下意识会避开那些刁钻的边缘输入。

于是我专门建了一个完全独立的测试仓，使用独立虚拟环境、100% 离线运行，定下两条铁律：

1. 测试只读取主系统的公开接口和真实返回，不为了凑绿灯去修改或跳过断言；
2. 遇到边界模糊的异常输入，遵循 **“拒绝优先”**——要么明确失败、记账、拦截，要么证明系统在契约层彻底安全，绝不允许静默吞掉或半截放行。

第一轮红队测试（102 条用例）跑下来，直接打爆了 **16 条失败、确认了 14 个真实缺陷**。下面这四类是最典型的坑：

| 编号 | 级别 | 暴露出的真实缺陷 | 修复策略与核心改动 |
| :--- | :--- | :--- | :--- |
| `FIND-001` | 高 | 失败的执行尝试消耗了 Token，却没有计入总预算账本，导致预算超发仍能继续循环重试 | 确立 `DEC-019`：失败尝试同样计费；确立 `DEC-022`：派发前做额度预留与在途准入控制 |
| `FIND-011` | 高 | 路径安全校验防住了 `../` 与软链接，但在 macOS 大小写不敏感文件系统下被 `.GIT/config` 绕过 | 路径规整与敏感目录比对统一归一化大小写，再做规范化边界判定 |
| `FIND-013` | 高 | 沙箱外文件通过硬链接（hard link）挂载进工作区，直接写入会逃逸修改宿主文件 | 在文件写入前检查链接计数与挂载边界，拒绝越界硬链接写入 |
| `FIND-014` | **P0** | 进程遭遇 `SIGKILL` 后调用 `resume` 恢复，被中断的任务没有重新入队派发，系统误判为“无可执行节点→死锁取消”，最终 `0/4` 全部白跑 | 重写恢复状态机（`RUNNING \| REVIEW -> FAILED -> READY`），且必须在**死锁判定之前**完成孤儿认领清扫（orphaned-claim sweep） |

> 尤其 `FIND-014` 很致命：没有专门写一条“先 `SIGKILL` 再 `resume`”的集成测试，平时所有 mock 超时、抛异常的测试全是绿的；唯独真的强杀进程重启后，整个图因为残留的 `running` 标记卡死并触发了误报死锁。

修完这一批问题后，后续红队测试扩充到 **116 条用例**。到了第三轮验收时，结果变成 **116/116 全绿（0 failed / 0 error / 0 skipped）**——14 个已确认缺陷全部闭环，连续 3 轮全量通过，其中针对 `SIGKILL -> resume` 的 6 条专项恢复测试也全部一次过关。

## 四、回头看这套系统真正沉淀下来的东西

多 Agent 系统最迷人的地方，往往是对话里看上去很聪明的涌现；但它能稳定交付的前提，却全是再朴素不过的老手艺：

- **预算不能靠“事后统计”**，必须在派发前做预留准入（in-flight admission），连失败的账也要老老实实记进账本；
- **状态机必须能从“断电瞬间的尸体”里爬起来**，先清扫孤儿现场，再做后续调度判断；
- **文件边界的校验永远按最坏的宿主环境算**，把软链接、硬链接和操作系统大小写差异一起锁死；
- **永远留一个和开发脑回路隔离的红队验证集**，它会专门挑你不想写进主干逻辑的脏输入来敲门。

先把“一定不能坏”的底线焊死，上面的智能调度才真正有意义。
