写作和排版分发，本来是两件完全不同频的事。写完一篇 Markdown 文章之后，如果还得分别搬进博客仓库、重新贴进微信公众号后台调缩进、再拆一版图发去别的平台，精力很快就会被重复劳动磨光。

与其去买一堆带黑盒云端存储的 SaaS 排版工具，不如自己用熟悉的技术栈拼一个**本地优先（Local-First）的多端发布工作台**，顺便把平时读了多少书的数据也流进自己的个人看板。

## 一、核心原则：以文件为数据库，严格止步于“草稿箱”

整套工作台的架构克制得几乎有点保守，定死了三条规矩：

1. **文件即数据库（File as Database）**：不专门架设重型数据库。每篇内容对应一个目录，配一份记录平台投递状态的 `meta.json` 和按平台隔离的渲染产物目录 `platforms/`，备份、版本控制和人工救急全靠直接读文件就能解决。
2. **只推到草稿箱，绝不自动群发**：无论是公众号还是图文草稿，脚本职责到“把格式完整的草稿和配图送进后台草稿箱”为止。真正的点击发表永远留给人工最后看一眼——哪怕只为了防止排版翻车或误发测试文本。
3. **严格区分 `failed` 与 `uncertain` 状态**：这是分布式投递最容易忽略的角落。网络超时或响应截断时，对方服务器可能已经创建了草稿，也可能没创建。这类状态会被标成 `uncertain`（不确定），系统**绝不自动盲目重试**，必须人工去后台确认一眼再推进，避免一觉醒来草稿箱里躺着五篇一模一样的重复稿件。

## 二、和个人订阅号 API、微信富文本死磕的实录

工程上最花时间的部分，全在微信公众号这一侧。自 2025 年 7 月起，个人订阅号在权限与环境上的限制变得非常具体：

- 官方标准的 `draft/add` 接口直接返回 `48001 api unauthorized`；
- 大多数面向服务器端的官方接口，在没有固定公网 IP 白名单的本地环境里会直接吃 `40164 invalid ip`。

既然走不通纯服务器 API，换一条思路也就顺理成章：**直接在本地复用自己已登录网页后台的会话（cookie / token）去调 `cgi-bin` 路径下的 `operate_appmsg` 与 `filetransfer`。** 只要把会话保活与状态校验做好，草稿写入和本地图片上传一样能跑通自动化流水线。

接口通了只是第一关，真正让人头皮发麻的是微信富文本编辑器的 HTML 清洗规则——桌面浏览器里看着好好的语义化 HTML，贴进微信后台瞬间变样：

| 标准 Markdown / HTML 写法 | 微信编辑器真实吞吐行为 | 工作台渲染器的针对性改写方案 |
| :--- | :--- | :--- |
| `<ul>` / `<li>` 嵌套列表 | 部分层级和圆点标记被编辑器吃掉，缩进塌成一坨文本 | 扁平化拆成带 `•` 前缀的独立段落与可控左边距 |
| 裸露的 `<br>` 换行标签 | 经常被清理或合并，段落间空行消失 | 统一改写为 `<span leaf=""><br></span>` 保留结构占位 |
| 指向外部非微信域名的 `<a>` 链接 | 直接拦截报错或被strip，整篇草稿无法保存 | 解析时自动检测域名，非微信域外链降级为普通文本展示或尾注参考 |
| 正文内嵌本地图或外部图床 URL | 无法保存或外链裂图 | 预先通过 `filetransfer` 上传换取 `mmbiz.qpic.cn` 托管地址后再回填 HTML |
| 剥离标签后超过 20,000 字符的长文 | 后台直接拒绝接收 | 构建阶段前置字数预警，超过阈值提示拆篇，避免压线超时失败 |

把这几条怪癖一一封进转换器之后，写好本地 Markdown 一键导出到公众号草稿箱，预览效果基本能一次对齐，省掉了大量手动调空格和逐张传图的机械动作。

## 三、顺手把微信读书数据接入博客个人看板

做完分发流，另一个一直想打通的是“输入流”——博客右上角的在线个人仪表盘（board）里既然已经有断食和运动记录，怎么能少掉每天都在翻的微信读书？

微信读书官方开放了一套 Agent Gateway 接口，核心路径集中在 `https://i.weread.qq.com/api/agent/gateway` 下面的三个端点：

- `/readdata/detail`：拉取阅读时长与近期阅读分布；
- `/shelf/sync`：同步当前书架与在读书单；
- `/book/getprogress`：拿到单本书的阅读进度。

接完测试才发现一个小坑：在个人账号的返回体里，`recordReadingTime` 字段始终返回 `0`。如果不做兼容处理，看板上的阅读时长就一直显示挂零。改成优先兜底回退读取 `readingTime` 字段后，进度和累计分钟数就立刻对上了。

为了不频繁打上游网关、也保证页面刷新响应够快，服务端在前面加了一层 **5 分钟内存 TTL 缓存**——把书架、近期阅读细节和单本进度聚合成看板仪表盘需要的轻量化 JSON。点开首页的阅读徽章，终于能直接看到正在读的书名和真实进度条，而不再只是一个冷冰冰的占位数字。

---

回过头看，这套工作台并没有用到什么高深框架，但它让我彻底把写作环境留在了自己最顺手的纯文本和 Git 仓库里：**写字只管写字，脏活交给转换器去和各个平台的怪脾气对线。**
