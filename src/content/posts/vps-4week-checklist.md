个人折腾云主机，最常见的误区是**刚拿到机器急着跑业务，三个月后机器彻底失联或者磁盘爆满，才发现根本不知道问题出在哪一层**。

针对最常见的入门配置——一台 **2GB 内存的 KVM VPS（Debian 13 `trixie`）**，我给自己梳理过一份按周推进的实操清单。不求大而全的企业级架构，但求每一项都有验证命令、每一个容灾开关都亲手打断测过。（下文均用 `<IP>` 与 `demo.example.com` 指代示例目标。）

## Phase 0：装软件之前的生存底线

机器刚开机，先做三件保命的底座配置：

- **先验网络质量**：从本地跑通 `ping` 与 `mtr` 看清丢包与路由跳数，确认底盘是否值得放服务。
- **补一条 2GB `swapfile` 并设 `vm.swappiness=10`**：2GB 物理内存在构建镜像或突发峰值时非常脆弱，没有 Swap 的话内核 OOM Killer 会直接一刀杀掉数据库；把 `swappiness` 压低到 `10`，既能让平时尽量走物理内存，又在尖峰时多一道缓冲垫。
- **打开 BBR 与队列调优**：在 `sysctl` 中启用 `bbr` 拥塞控制、`fq` 队列规则，并将 `somaxconn=4096` 拉高，避免高并发短连接握手直接卡在默认队列上限上。

## 第一周：安全边界、守护进程与反向代理

| 模块 | 关键动作 | 不可省略的验收手法 |
| :--- | :--- | :--- |
| **SSH 密钥化** | 本地生成 `ed25519` 密钥对，配置 `sshd` 禁用密码登录（`PasswordAuthentication no`） | **重启 `sshd` 后必须保留当前已连接终端先不关**，新开一个窗口验证免密登录后再退出旧会话，防止把自己反锁在门外 |
| **边界防火墙** | 开启 `ufw` 仅放行 `22 / 80 / 443`，联动 `fail2ban` 自动封禁暴力扫端口 IP | 从外部检查关闭端口不可达，查看封禁计数日志正常递增 |
| **进程守护与隔离** | 业务用 `systemd` 托管，启用 `NoNewPrivileges`、`ProtectSystem=strict` 与 `MemoryMax=256M` 硬上限 | **直接对主进程执行一次 `kill -9`**，确认几秒内被 `systemd` 自动拉起，而不是只看 `systemctl status` 绿灯 |
| **HTTPS 入口** | Nginx 反向代理本地端口 + Certbot 自动签发与续期证书 | 验证 `http://demo.example.com` 跳转及 TLS 证书自动续期 dry-run 通过 |

## 第二周：容器体积、日志限额与“真做过恢复”的备份

2GB 机器跑 Docker，最容易翻车的往往不是 CPU，而是**没人管的容器日志在后台悄悄吃光整块硬盘**。

- **全局限制 Docker 日志**：配置 `json-file` 驱动的日志轮转策略（`max-size: 10m`、`max-file: 3`），把单个容器日志体积永久封顶在 30MB 内。
- **多阶段构建控制体积**：用多阶段 Alpine `Dockerfile` 把业务运行镜像压到 **100MB 以内**，拉取和重启速度差一个量级。
- **数据库健康门禁与恢复演练**：Postgres 容器通过 `service_healthy` 声明健康检查门禁，应用层等数据库真正就绪再启动；定期通过定时任务运行 `pg_dumpall` 归档，而且**强制规定备份必须跑通一次完整 Restore 演练并测算实际 RTO**——从来没恢复过的备份文件，不能算做过备份。

## 第三周：轻量化监控与压测归因

不想让监控套件反客为主吃光 2GB 内存，给 Prometheus 配上硬保留上限（保留 **15 天** 或 **2GB 存储上限**），挂上 `node-exporter` 和 Grafana 经典看板（Dashboard ID **`1860`**），日常只紧盯四个信号：

1. **CPU `steal`**：同宿主机有没有“吵闹的邻居”在疯狂抢占物理核时间片；
2. **`MemAvailable`**：内核真正可回收调度的可用内存余量，而不是被 `free` 迷惑；
3. **`files_free`**：inode 剩余量——很多时候磁盘空间才用到 60%，但小文件太多先把 inode 耗光导致照样无法写入；
4. **`CurrEstab` / `TCP_tw`**：当前活跃连接与 `TIME_WAIT` 堆积情况，判断连接池是否泄漏或端口耗尽。

压测时直接用 `ab` / `hey` 打流量，同时终端并排挂着 `vmstat`、`ss`、`htop`、`iotop`——一旦延迟飙升，第一时间分辨出瓶颈卡在 CPU 计算、磁盘 IO 等待、还是 TCP 队列。

## 第四周：从 DNS 到抓包的逐层定位练习

最后一周不加任何新功能，专门用来练“断链定位”：

- **`dig +trace`**：从根域名服务器往下逐级核对解析链路，排除缓存污染与记录生效延迟；
- **`curl -w` 耗时拆解**：把一次请求冷冰冰地拆成 `dns` / `tcp` / `tls` / `ttfb` 四段毫秒数，接口慢到底是解析慢、握手慢，还是后端代码慢，十秒定性；
- **`tcpdump` 抓包与五类常见故障演练**：针对进程崩溃、端口冲突、磁盘满、证书失效、上游超时各手动制造一次现场再复原；再对照服务器月流量包算好带宽余量，自问五个兜底问题（密钥丢了怎么进、整机炸了多久能迁走、半夜谁告警、日志在哪翻、账单突增怎么止损）。
